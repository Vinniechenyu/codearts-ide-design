CORE VERDICT

真正该拆开的是责任、方法链和验收标准，不一定是入口

后台应有两套清晰的能力编排和质量闸门；前台保留统一任务入口，由系统根据任务对象、复杂度和验收标准自动路由。

专家中心可以展示两个专家，但必须用任务语言解释差异，不能只靠专业名称。

HTML 创作专家让一份内容更值得被看、被理解和被使用；产品体验设计专家让一个产品更值得被做、被操作和被持续演进。
01
它们解决的不是同一个问题

一个解决「已有内容如何变成更易理解、可交互、可分享的网页成果」；另一个解决「一个产品应该服务谁、如何完成任务、界面与状态如何组织，以及最终是否真正可用」。

02
核心人群部分重合，但主任务不一致

两者都服务产品经理、运营、项目经理与企业内 AI Maker；HTML 创作还明显偏向咨询、售前、研究、培训、业务分析，产品体验还明显偏向产品负责人、设计师、研发。

03
拆的是责任与验收，不是入口

只有当两者拥有不同的任务回放字段、阶段计划、质量闸门、交付包、转交条件和成功指标时，拆分才真正产生价值。

RISK 01

两个名称仍然难以区分

「HTML」是技术格式，「产品体验」是专业领域，两者不在同一命名层级。用户可能误解成「HTML 专家只会写代码」「漂亮网页都该找产品体验设计专家」。

对策副标题与快捷任务讲清价值；系统按任务自动推荐，不要求用户理解术语。
RISK 02

只换角色包装，共用同一套生成能力

如果两者都只是调用同一个网页生成 Prompt，拆分没有价值，还会增加认知成本。

对策必须以六项证据证明差异：不同任务回放字段、阶段计划、质量闸门、交付包、转交条件、成功指标。
RISK 03

边界任务反复跳转

「做一个企业官网」「做一个数据看板」「做一个计算器」都可能位于边界，来回转交会让用户重复解释。

对策不按产物名称静态分类；用「是否定义用户与流程、是否改变业务状态、是否持续运行」判断；只有边界实质变化才转交，且保留全部上下文。
RISK 04

产品体验设计专家过重

如果所有产品体验任务都强制经历完整研究、UX、UI、实现与验收，简单局部优化会变慢。

对策内部继续区分单专家轻路径与专家团完整路径——拆成两个专家，不等于每个专家内部只能有一种流程。
RISK 05

HTML 创作专家沦为模板生成器

如果只提供主题模板和页面风格，它无法证明专业价值——视觉只是表达层，不是它的全部价值。

对策重点建设资料理解、数据对账、来源绑定、内容结构、预览中局部修改、安全分享与周期复用。

Recommended Naming

HTML 创作专家

把文档、表格和业务资料变成可打开、可交互、可分享的网页成果。

为什么是「创作」而不是「生成」：「生成」是机器动作，只承诺吐出一段代码；「创作」是人的工作——理解资料、组织结构、选择表达，产出一份能打开、能追溯、能分享的作品。副标题必须跟上，不要写成「帮你生成 HTML 代码」——普通办公用户会误判为开发者工具。

01

领域角色 + 固定规范

不是「生成一个漂亮网页」，而是定义角色背景、工作目标、技术要求、设计规范与输出格式，把易漂移的自由生成压成稳定的场景模板。

领域知识 + 内容结构 + 视觉规则 + 技术约束 + 输出格式 = 某一办公场景的 HTML 专家
02

解析与生成拆开

先用文档解析工具把表格、公式、版面、图片转成机器可处理内容，再交给模型。解析工具负责「读出来」，模型负责「分析和表达」。

对办公场景而言，这比继续调提示词更重要——用户输入往往是多个文件，不是一句话
03

结构化提取兜底

模型产出 HTML 后加一层参数提取，只保留代码、过滤解释文本。承认模型输出是不稳定的中间结果，必须处理后才能进入文件生成。

「生成内容」与「形成可用成果」之间存在质量闸门
04

代码转成真实成果

后端接收内容、生成文件、落到存储、返回地址；扣子空间同类案例直接呈现预览或分享页，而不是让用户复制代码、建文件、起服务。

用户拿到的是能打开的东西，不是一段代码块
还有一条产品级经验：扣子空间把「网页模式」用于文献研究报告、参考文献生成器、论文版本对比、旅行攻略与互动手册、交互式课程、动态图表与图文故事——共同点不是「都要做网站」，而是静态文档不够直观、传统办公软件做交互又太重，于是用轻量网页承载内容、数据和少量操作。复杂任务还会先规划、用户确认后再执行。

30-SECOND VERSION
HTML 创作专家和产品体验设计专家虽然都可能生成网页，但解决的不是同一个问题。前者从文档、表格和数据出发，目标是把内容变成可信、直观、可分享的网页成果；后者从产品想法、功能需求或现有体验出发，目标是把用户流程、视觉系统和可运行前端组织成一个可验证的产品。两者的职业人群部分重合，但用户任务、专业判断和验收标准不同。因此建议能力和责任分开建设，用户入口保持统一，由系统自动路由，并在任务升级时携带完整上下文转交。
同样交付网页，HTML 创作专家对「内容是否讲清楚」负责，产品体验设计专家对「产品是否做正确」负责。

不同质量闸门内容数据运行体验安全 vs 对齐逻辑视觉实现验收
05
不同成功指标被打开分享复用 vs 被验收并继续投入
不能只因为：都有市场案例、都能生成 HTML、希望专家市场看起来更丰富、想用不同角色形象包装同一能力。
目标人群按「任务」而不是「职位」定义：HTML 创作专家服务「需要把现有内容变成网页成果」的任务；产品体验设计专家服务「需要定义或改造数字产品体验」的任务。
分析依据与边界：① 一手实测——2026-08-05 在 Claude Directory、TraeWork 插件市场、WorkBuddy 专家/技能市场、千问办公技能市场分别搜索 html（第 11—12 页，可点击放大核对）。② 公开案例——火山引擎开发者社区的 AI 财报分析与 HTML 可视化工作流、扣子空间相关案例。③ 内部文档二次拆解——《码道Work-HTML生成专家产品方案-参考火山引擎实践》《码道Work-UIUX设计专家-用户使用旅程与能力编排方案》《五款AI工作平台-设计能力构建竞品分析》，未新增未经验证的用户研究数据或业务指标。结论只走到证据能支撑的地方：形态缺口与产品路径可证，生成质量、效率提升与路由认可度待同题实测。
