1

一道题，跑完五款

同一份真实 PRD 片段 + 同一个组件库，要求产出可运行的 Web 界面。不给提示词技巧，不允许中途补充需求，中间强制中断一次再续跑。

五条证据分别对应上一页的五个质量条件
① 理解是否主动问出目标用户、约束与成功标准，还是自行补全追问 / 假设 比
② 方法是否按任务类型选路，并能说明为什么走这条路径路径可解释
③ 状态强制中断后重开，前序决策与产物是否还能被消费恢复成功率
④ 工具是否真的打开浏览器 / Figma / 代码仓，而不是在文本里假设真实调用凭据
⑤ 证据产物能否跑起来、截图能否对上、未解决问题是否列明可运行 + 可对照
本页是待执行的实测协议，不是实测结果。本报告的全部结论建立在插件结构、官方功能、界面截图与本地套件代码之上——前面三页各有一句「不代表质量」的免责，说的都是同一件事。这道题同时是码道 Work 首条闭环的验收题：我们用来判竞品的尺子，必须先量得住自己。

用户只描述任务；运行时负责路由、阶段状态、依赖与恢复。每个能力声明输入/输出，只读写版本化设计契约，并由证据门禁控制完成状态。

为什么我们敢建更长的链：千问的四处漂移不是「链太长」造成的，是文本约定 + 无运行时校验造成的。同一条链，用 Schema 校验、字段权限与版本迁移承载，漂移就变成构建期错误而不是运行期事故。
